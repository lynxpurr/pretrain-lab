## 跨日回顾（Day 0~7，项目级 12 条——详细条目见下文按日追加）

1. **值域与锚定断言必须前置到数据侧**：编码处 O(秒) 的断言，抵得上训练侧 O(小时) 的排查（Day 1 表外字符穿透 → device-assert）。
2. **首步 loss = ln(V) 是免费复现锚，但容差随模型规模放宽**：22M +0.06 / 30M +0.08 / 140M +0.17；判据 = `ln(V)+0~0.25` 且不接近 0。
3. **无人值守跑批五件套**：tmux 脱离 + 滚动 ckpt + `--max-minutes` 兜底 + `EXIT:0/1` 标记 + **kill 一次验证续训**。"能跑"和"崩了能接上"是两件事。
4. **证据三分 + 指纹纪律**：md 摘要 / csv 曲线 / 原始 log，只增不改；每份数据与 ckpt 落位即录 sha256（可跨机对账、可防"跑完才发现数据被改"）。
5. **显存上限先算 loss 的 fp32 副本**：`positions × vocab × 6 bytes`（bf16 logits + 2×fp32）常常比参数/激活更大；梯度累积摊不薄它。
6. **决策门口径必须写清"在哪个模型、用哪段曲线"**，并配一个混杂诊断：门① 写清 140M 等效；门② 用恒定 lr 探针区分"lr 退火"与"数据饱和"。**指标不注明测量对象 = 没定义**。
7. **优化项一律先做单变量对照再归因**：torch.compile（4k vs 52k tok/s）、micro-bs 越大越快（false）、"greedy 放大复读"（false）——三次都是直觉错、对照对。同模型×同数据×只改一个变量，≥40 步读数。
8. **质量评估三件套**：关键词判分（覆盖）+ 质性抽样（正确性/格式）+ 退化指标（distinct-2/rep-4）。只看单一分数会把"复读 + 拒答模板"当成高分。
9. **操作安全两条**：长任务输出别用 `| head`/`| tail` 截断（SIGPIPE 杀进程）；`pkill -f <pattern>` 会命中自己的 shell（按 `/proc/<pid>/comm` 过滤或直接 kill PID）。
10. **先把库存/需求比算清楚再拍数据预算**：zh 3B 的 6:4 已用库存 72%，加训前必须先算账（否则跑到 90% 才发现只能改配比）。
11. **采样规则按能力域保护，不按表面格式一刀切**：列表降采样会误伤数学推理（v2 的 3+5=15、7×6=72）；先保护能力域，再压风格（v2b 修回 8/42，代价 rep-4 0.117）。**先问"这条样本在教什么能力"，再决定降不降。**（Day 8 深化：能力域内还可按**功能特征**收窄——教算术组合的是"等式行 ≥3 的练习列表"（9,693 条），不是"数学关键词"（26,184 条）；豁免口径从 23,253 收到 6,243，数学照样修回。）
12. **"能加载/能跑"不等于"语义对"**：GGUF 漏 q/k RoPE permute → 前几词正常、随后复读；评测 CSV 头/行错列 → rubric 静默空表；导出/评测链路必须拿 PyTorch/行字段断言对拍，才算验收。
13. **降采样/上采样的作用域是"训练集（读到的行）"，不是"全库"**：英文拒答全库 21,345 条中 16,601 条集中在一个 100k 行的桶里，而 250M token 预算在 n_read≈810k 截断——"砍 seen 的 50%"对训练效果等价于"砍训练集内拒答的 50%"，但对"全库"不是。**改 --max-tokens = 改训练分布**（读到的桶不同），采样规则 × 数据顺序 × 预算三者交互，改动前后必须 meta 对账。出处：`data/PROVENANCE.md` v2c 节 · 分桶扫描对账。

## 2026-11-18 · Day 0~1 · 环境预铺 + 字符级最小闭环

- **查表编码必须假设"输入字符集 ⊄ 表"——编码后值域断言是生死线**（Day 1 最大坑）：字符编码用 `str.translate` 提速（C 级查表），但它对**表外字符原样放行**；val 取自语料头部、含 train 未出现的字符，穿透映射后码点 >65535 被 uint16 截断成垃圾 id（实测 val max = 65025），直到训练端 embedding device-assert 才炸——数据 bug 跑进了训练阶段。修法 = 映射表覆盖 `set(train)|set(val)` + `encode()` 内断言 `ids.max() < vocab_size`。通用化：**值域断言放在编码处（数据侧），不放在训练侧**——数据管线收尾时是 O(秒) 的检查，进训练后是 O(小时) 的排查。出处：tools/prepare_char20m.py 编码段注释；LAB_NOTEBOOK Day 1。
- **device-side assert 异步上报，报错栈位置 ≠ 真凶**：CUDA assert 会在出错后的某个后续 kernel 处抛出（本例栈顶指到 RMSNorm，真凶是 embedding gather 的越界索引）。定位法 = `CUDA_LAUNCH_BLOCKING=1` 同步复跑，栈顶即真凶。出处：两次冒烟 trace 对比（logs/smoke/，CUDA_LAUNCH_BLOCKING 前后）。
- **初始 loss = ln(V) 是免费的复现检查锚**：随机初始化的 LM 起步 loss 应 ≈ ln(vocab_size)（均匀分布的熵）。本仓三次实证：冒烟 bs32 = 9.4297 / bs64 = 9.4316 / 正式 run = 9.4316，对 ln(11765) = 9.3727 同值域。**首步 loss 显著偏离 ln(V) ⇒ 编码/词表/取批必有 bug**——比"训不动才发现"便宜一个数量级。出处：logs/smoke/loss_curve.csv + 正式 run 日志首行（收波快照至 reports/）。
- **hf CLI `--include` 多 pattern 只吃第一个**（Day 0）：`hf download <repo> --include "a" "b" "c"` 从第二个 pattern 起被解析成位置参数文件名（告警 "Ignoring --include"），静默漏下大件。要么逐文件位置参数（`hf download <repo> file.jsonl`），要么 `--include` 传单个 glob。**教训：CLI 告警必须逐条读，"Ignoring/Deprecated" 类告警常伴随静默行为偏差。**出处：data/PROVENANCE.md 下载渠道备忘。
- **数据集现行名以 repo 实时清单为准，旧文档会过期**（Day 0）：minimind 数据文件 pretrain_hq/sft_512 → pretrain_t2t(_mini)/sft_t2t(_mini) 已改版，旧名 404；ModelScope 也无此库（"record not found"）。下单前先 `curl /api/datasets/<id>/tree/main` 核对文件清单，再对照官方仓 README 现行段。出处：data/PROVENANCE.md 下载渠道备忘 · `~/projects/minimind/README.md` L122-423。
- **训练跑批三件套 = 时间预算 + 滚动 checkpoint + tmux 脱离**（Day 1 实测 96 分钟零事故）：①`--max-minutes` 时间兜底让"到点收尾"成为预期路径而非事故（正式跑设 100min > 预估 96min，收尾时仍完整存盘并算终版 val）；②`--ckpt-every 2000` 保证任何中断最多损失 2000 步（≈6 分钟）；③tmux 托管 + `Ctrl+b d` 脱离，让"关闭终端"不等于"杀掉训练"——**这三件是无人值守跑批的最低配置，缺一即把可控实验变成赌博**。补充坑：训练进程运行中重命名其代码目录（本次 src→tools）不会影响已加载的进程，但会破坏任何运行中的相对路径读取（如中途 import/重载）——**改名放到跑批结束后做**。出处：tools/train_char20m.py 参数段 · LAB_NOTEBOOK Day 1。
- **证据三分法：摘要 md + 曲线 csv + 原始 log**（Day 1 起用，30 分钟定稿）：`reports/` 每次 run 落三件——①摘要 md（配置/里程碑表/采样对比/复现命令，人读）；②曲线 csv（每 log/eval 一行，机读可再分析）；③原始 stdout（完整现场，争议时的终审证据）。只交摘要会丢现场，只交 log 则无法快速对账——**三者成本几乎为零（cp 三条命令），却把"事后能否复盘"从运气变成必然**。出处：reports/2026-11-18-day1-char20m.{md,csv,log}。
- **loss 是量化信号，采样是质性信号——两者必须同时看**（Day 1）：val 从 2.04 单调降到 1.56 全程"健康"，但采样才暴露出短 prompt 长续写的模式坍缩（"教堂"复读）——这个缺陷 loss 曲线完全看不见。**跑批时每 1000 步固定 prompt 采样并留在 log 里，收波时对比不同 step 的同一 prompt**，才能同时回答"学得好不好"（loss）与"学成了什么样"（采样）。出处：reports/2026-11-18-day1-char20m.md §3 采样进化链。

## 2026-11-18 · Day 2 · tokenizer + memmap 数据流水线

- **BPE 训练成本按"语料词数"放大，不按字节线性**（Day 2 实测）：600MB 中英混采训 32k merges → 271s、峰值 RSS **~22GB**；HF `train_from_iterator` 先做全量词频统计，内存与"word 单元数"成正比（中文按字切、英文按词切）。小机器上 100~300MB/语言是合理折中。另：`show_progress` 的 tqdm 在 `tee` 管道下不落盘——**日志没进度 ≠ 进程卡死**，先看 CPU/RSS（本次 300~450% CPU、20GB RSS 属正常计算态）。
- **`decode()` 默认 `skip_special_tokens=True`——往返自检必须显式 False**（Day 2 首次跑挂）：探针里混入 `<|endoftext|>` 字面量时，编码被识别成 special id，解码默认把它吞掉，往返断言莫名失败。修法 = 探针拆两段：①普通文本（含 emoji/生僻字/零宽字符）验 byte-level 无损；②specials 单独 `decode(..., skip_special_tokens=False)` 验编号与解码。出处：tools/train_tokenizer.py 自检段。
- **混配比按 token 级缺口调度，不按字节/文档估算**（Day 2）：压缩率随语言/内容变化（同语料 zh 1.84 / en 4.23 chars/token），先估 chars 再换算引入误差；`build_shards.py` 每编码一篇文档就按"目标比例×(总量+1)−已累计"选语言，3B 实际落成 en 60.0% / zh 40.0%（偏差 <0.01%）。val 用 `hash % 500` 做**文档级**划分：随机、可复现、不依赖读取顺序，且与 train 天然不共享文档；预算满后多余候选**丢弃**而非塞回 train——否则"留出集"名存实亡。出处：tools/build_shards.py 注释段 + reports/2026-11-18-day2-shards.md §3。
- **分片大小的决定因素是"指纹/校验/增量重建成本"，不是"能否全进内存"**（Day 2 拍板）：3B token 全量才 6GB，96GB 内存显然装得下，但仍选 1GB/片——单文件 6GB 会让每次校验/重建都要动整块；1GB×6 片 + val 共 7 条 SHA256，`sha256sum -c` 3.5s 全量对账，坏一片只重跑一片。**"内存放得下"回答的是能不能，分片回答的是坏了以后赔多少。**出处：HANDOFF §7 Day 2 决策点③ + reports/2026-11-18-day2-shards.md §2。

## 2026-11-19 · Day 6 · 门② 判定与解码对照

- **"greedy 放大复读"是错的——先做对照再归因**（Day 6 证伪 Day 5 的猜测）：Day 5 看到 greedy 下"文化/艺术/交通"复读环，我推断"贪心解码放大复读"。Day 6 用同模型同题库跑 5 个解码配置：greedy rep-4 **0.131** vs 采样（T0.7/top-p0.9）**0.123**——几乎没差。**复读来自 SFT 数据的罗列式答案风格，不是解码**。通用教训：**质量缺陷先做"单变量对照"（同模型×同题×换解码/换数据），再写归因**；凭直觉归因会把修复方向带偏（这次差点去做无用的解码调参）。出处：reports/2026-11-19-day6-decode.md §1~2。
- **repetition penalty 是"用事实换多样性"的交易，要画权衡曲线**（Day 6 实测）：rp1.1 → rep-4 0.087 / 题库 15；rp1.2 → 0.057 / 15；rp1.3 → **0.032 / 13**。罚得过重会把必须复述的 token（如"H2O"）也压掉、把正常回答变成拒答。**任何"后处理调参"都要同时报主指标和退化指标，并给出拐点**；单一分数最优的参数往往不可用。出处：同上 §1。
- **门② 这类"趋势判定"要配一个混杂诊断，而不是只信单一口径**（Day 6）：预注册量"最后 10% 降幅 0.0134"落在 cosine 退火区间（lr 7.3e-5→6e-5），无法区分"lr→0"与"数据饱和"。补齐方法 = 恒定 lr 探针（300 步 @6e-5，从 90% ckpt 起），得 0.0051（且是重置 Adam 动量后的乐观上界）。**两条独立证据同向才落判定**；若背离，报告里两个数都写、并说明各自的口径与偏差方向。出处：reports/2026-11-19-day6-gate2.md §2~3。
- **评测协议 = 解码参数 + 判分规则 + 退化指标，三者缺一不可**（Day 6）：只报"16/18"会同时掩盖复读（rep-4 0.131）与校准失败（编造未来事件）。定档 = 统一 greedy（可复现）+ 关键词判分 + distinct-2/rep-4 + 人工 rubric 抽样；**demo 端可换采样参数，但要在报告里单独声明，不能混进同一张对比表**。出处：reports/2026-11-19-day6-decode.md §3 · tools/eval.py。

## 2026-11-19 · Day 5 · SFT 与评测

- **规则判分会系统性高估质量——评测必须"规则分 + 质性复核"双轨**（Day 5 实测）：18 题关键词命中判分给出 16/18 = 89%，但人工复读发现：`fact-capital-cn` 尾部"文化、艺术、交通"复读环、`fact-months` 编造"春季月数比夏季多"、`math-mul` 无视"只回答数字"、`translate-en2zh` 用英文回答、`en-fluency` 触发"我无法提供…"拒答模板却因正文含关键词被判过。**关键词判分只测"是否提到"，不测"是否正确/是否遵循格式/是否退化"**。修法 = 加自动退化指标（distinct-2、最长重复片段）+ 人工 rubric 抽样复核，二者并列呈现。出处：reports/2026-11-19-day5-eval.md · LAB_NOTEBOOK Day 5 补记。
- **greedy 解码会放大复读环，评测默认解码策略必须写进报告**（Day 5）：SFT 模型在 greedy 下出现"文化、艺术、交通、金融…"环，而训练日志里 temp 0.8/top_k 200 的采样反而更自然。结论要用固定解码协议（Day 10 三版对比统一 greedy 或统一采样），**且解码参数本身就是质量变量，不能只报分数不报协议**。出处：tools/eval.py `chat()` · `model.generate(greedy=True)`。
- **SFT 的遗忘成本要显性量化，不能只看 SFT 指标变好**（Day 5）：预训练 PPL 15.350 → 16.307（**+6.2%**），SFT PPL 9.818 → 4.596（2.1×↓），题库 33% → 89%。混入 25% 预训练块只部分抵消遗忘。**报告与模型卡必须并列 base/SFT 双口径**（语言能力保留 vs 指令跟随），否则"SFT 后全面变好"是错觉。出处：reports/2026-11-19-day5-eval.md 汇总表。
- **1 epoch 就饱和的 SFT，先查数据质量再谈加 epoch**（Day 5）：SFT val 1.7658@250 → 1.6217@1500 → 1.5515@3815，末 1,000 步只降 0.006；同时质性缺陷集中在数据风格（罗列癖/拒答模板）。**"再加一个 epoch"通常只是把数据缺陷学得更牢**；正确顺序 = 解码对照 → 数据过滤/加权 → 最后才加 epoch。出处：logs/sft-v1-tty.log · LAB_NOTEBOOK Day 5 疑问。

## 2026-11-18 · Day 4 · SFT 数据/脚本 + 主训练起跑

- **`pkill -f <pattern>` 会匹配到"包含该 pattern 的自己的 shell"**（Day 4 第三次自伤）：`pkill -9 -f "run-name _preflight"` 把执行这条命令的 bash 一起杀了（bash 的 cmdline 里正含着这段字符串），表现为"命令无输出、后台任务莫名其妙结束"。安全姿势 = 先 `pgrep -f` 拿 PID，再用 `/proc/<pid>/comm` 过滤出真正的解释器进程（`comm == python`）后按 PID kill；或者直接用会话管理器（`tmux kill-session`）。**杀进程前先问：我的过滤条件会不会命中我自己？**出处：Day 4 预检清理现场 · logs/_preflight（EXIT:1）。
- **SFT 打包必须"会话不跨块"**（Day 4 第一版实现缺陷）：把 token 流按 1024 硬切，会把一条对话切成两半——后半段没有 `<|im_start|>` 头，模型在缺失上下文的 fragment 上算 loss，语义被污染且无法用段级断言校验。修法 = 当前块装不下整条会话就补 EOS 收块、下块重开（本例 ~13% 填充）。**"打包提效"的正确姿势是提高块利用率，不是牺牲样本完整性**。出处：tools/build_sft.py `BlockWriter.add_conversation`。
- **SFT mask 必须用"段级断言"验证，不能只看监督比例**（Day 4 自检）：比例 0.78 看起来合理，但比例对不代表语义对。可执行的断言 = 枚举每个 `<|im_start|>`…`<|im_end|>` 段：user 段内 label 全 -100；assistant 段内 `label[i] == token[i+1]`；assistant 段末位置 `label == <|im_end|>`(=2)；块尾 label 全 -100。本例 150 段 0 违规才算过。**掩码类数据的验收标准是"逐段可枚举的恒等式"，不是"均值像那么回事"。**出处：Day 4 验证脚本输出（150 段 / 75 assistant / 0 违规）。
- **val 留出率直接决定构建时要读多少盘**（Day 4 踩坑）：`val-mod=100` 意味着每 100 条留 1 条，要凑 2M val token（约 7.5k 条）就得读 ~75 万行（全库 905,718 行的 83%）。第一版测试用 `val-mod=500` + `val-tokens=4e5`，要读 75 万行才凑够，看起来像"脚本卡死"（100% CPU 两分钟）。**设计 val 预算先算：需要 val token ÷ 平均每会话 token × val-mod ≈ 必读行数**；测试时用 `val-mod=100 + 小 val-tokens` 才跑得快。出处：logs/day4-sft-build.log（100k 行/0.7 min 的线性进度）。
- **eval 的 batch size 要单独预检，不能从训练峰值外推**（Day 4）：训练 bs8 峰值 10.51GB 不代表 eval bs16 也安全（forward-only 无梯度，但 CE 的 fp32 副本仍按 positions×vocab 增长）。起跑前用同命令 + `--max-steps 2 --eval-batch-size 16` 预检，peak 仍是 10.51GB 才放心。**"训练能跑"不等于"eval 能跑"，第一次 eval 往往在几十分钟后，炸掉的代价是重跑。**出处：Day 4 预检（`[val] loss 10.5203 | peak 9.49 GB`）。
- **早期 loss 不能用短探针线性外推**（Day 4 预判失误）：探针 40 步 val 8.92 → 我按"每步固定降幅"预估 500 步在 8.5~9.0，实测 **4.9742**。原因：40 步只有 2.6M token，loss 在 warmup 早期下降最快（学习率还在爬升、模型在拟合高频统计），外推必须按"token 数"而非"步数"，且要承认曲线是凸的。**给预测区间时必须写明"基于多少 token / 哪一段曲线"，否则区间是装饰品。**出处：logs/main140m-*.log step 500。

## 2026-11-18 · Day 3 · 训练框架 / 显存账 / 续训

- **`map_location` 会把"非权重张量"也搬上 GPU——续训的 RNG 状态必须显式 `.cpu()`**（Day 3 实测）：`last.pt` 里存了 `torch.get_rng_state()`（CPU ByteTensor），`torch.load(..., map_location="cuda")` 按"所有张量"统一搬运 → `torch.set_rng_state` 抛 `TypeError: RNG state must be a torch.ByteTensor`。修法 = `ckpt["torch_rng"].cpu()`（cuda RNG 状态同理）。通用化：**checkpoint 里的"控制类张量"（RNG/计数器/掩码）与"计算类张量"（权重/优化器态）设备语义不同，加载时要分开处理**。而这条只有在"kill 一次验证续训"时才会暴露——清单里的验证步骤不是仪式。出处：tools/train.py 续训段 · reports/2026-11-18-day3-framework.md §4。
- **16GB 卡上卡住 micro-batch 的常是 loss 的 fp32 副本，不是参数也不是激活**（Day 3 实测）：140M 参数+优化器态 2.2GB，但 `lm_head` logits 在 autocast 下有**三份**——bf16 logits（B·T·V·2）+ `F.cross_entropy` 内部升 fp32（B·T·V·4）+ 为反向保留的 log_softmax（B·T·V·4）。bs16×1024×32000 时 ≈5.25GB，bs24 单份 3.14GB 直接 OOM。**梯度累积摊不薄它**：CE 逐 token 独立，micro-batch 内所有位置一次算完才 backward（累积省的是 batch 维度重复，不是单次前向的 logits 体积）。推论：估显存先算 `positions × vocab × 6 bytes`（bf16+2×fp32）；想提 bs，优先砍 CE 副本（自定义 autograd/分块），而不是加激活检查点。出处：reports/2026-11-18-day3-framework.md §3 · memsweep.log 的 OOM 原文。
- **micro-batch 不是越大越快——先测再定，判据是 tok/s 而不是 batch 大小**（Day 3 实测 140M @T1024）：bs8 = 52,250 tok/s（峰值 10.51GB）> bs10 = 51,230（12.56GB，需 expandable_segments）> bs16+grad-ckpt = 40,449（8.84GB，重算 −23%）。bs8 已经喂满 SDPA（T=1024 时注意力占比高、每步 8k token 足够），再加大只是逼近显存上限并放大 allocator 抖动；grad-ckpt 用 23% 的算力换 1.7GB 是最差交易。**"更大 batch 更好"是直觉陷阱，必须用同口径 40 步以上的稳定段读数裁决。**出处：reports/2026-11-18-day3-140m-probe.md §3。
- **`torch.compile` 在新架构上要先测后信**（Day 3 负面结果）：140M/bs8 下编译版 **4,077 tok/s**，约为 eager 基线的 1/13；首步编译 18s 后每步仍 ~1.5s（eager 0.16s）。sm_120 + SDPA 的 inductor 代码生成未走快路径。通用化：**性能优化项一律以"同配置、≥40 步、扣掉编译时间"的读数裁决**，否则容易把"应该更快"当结论。出处：reports/2026-11-18-day3-framework.md §5。
- **首步锚 ln(V) 的容差随模型规模放宽**（Day 1~3 三点实测）：22.2M 字符级 +0.059、30M BPE +0.081、**140M +0.170**。初始 logits 方差来自残差流逐层累积（层越多偏离均匀分布越远），ln(V) 是"无限宽/无限浅"的极限值。判据 = 首步 loss 落在 `ln(V) + 0~0.25` 且不接近 0 即正常；明显偏低（"见过答案"：标签错位/重复数据）或偏离 >0.5 才停线。出处：reports/2026-11-18-day3-140m-probe.md §5。
- **长跑的输出管道不能被 `head`/`tail` 截断——SIGPIPE 会杀死训练进程**（Day 3 两次自伤）：`python train.py ... | head -13` 在 head 读够行后关闭管道，训练侧 `print` 抛 `BrokenPipeError` → 进程以 EXIT:1 退出，看起来像"训练崩了"，实际是我的观察方式杀的。长任务一律 `> log 2>&1` 或 `| tee`，观察用 `tail`/`grep` 读**文件**；判活看 exit 标记与产物增长。附带教训：**探索跑/对照跑的 log 也是证据**——写报告前不要 `rm` 临时 out/log，至少留到收波，本次 bs10/bs16gc 对照因先删后补跑多花 3 分钟。出处：logs/day3-resume-*（EXIT:1 现场）· reports/2026-11-18-day3-memsweep.log（补跑留存）。

## 2026-11-18 · Day 2 盘点校准批 · 跑批观测与 spec 写作

- **长任务轮询先清 stale exit 标记，判活看 PID/CPU/产物增长**（Day 2 实测）：第一次 tokenizer 跑挂在自检上、留下 `logs/day2-tokenizer.exit=EXIT:1`；第二次启动后我直接读到旧标记，误判"又失败了"。另外 `tee` 管道下 tqdm 进度不落盘、日志 mtime 也不动，**"日志没更新"同样不能作为死亡判据**。正确姿势 = 启动前 `rm -f <exit marker>`；判活看 `ps -o pid,etime,%cpu,rss` + 输出文件/目录是否增长。出处：logs/day2-tokenizer-* + LAB_NOTEBOOK Day 2 补记。
- **证据 log 会被 `*.log` 静默吞掉——收波必须 `git add -n` 核对三件套**（Day 2 盘点发现）：Day 1 报告白纸黑字引用 `reports/2026-11-18-day1-char20m-train.log`，但 `.gitignore` 的 `*.log` 让它从未入库——跨机复现时"证据链"直接断。修法 = `.gitignore` 加 `!reports/*.log`；**收波检查从"文件在磁盘上"升级为"文件在 `git add -n` 列表里"**。出处：.gitignore · commit `79ae2fe`。
- **建库前先算"token 库存/需求比"，再拍 token 预算**（Day 2 校准）：用 tokenizer 留出集的 `bytes/token` × 语料磁盘字节数估全库 token——本次 zh ≈1.66B、en ≈6.54B；3B 的 6:4 要 zh 1.2B = **72% 库存**，门②再加 1.5B 就告急。**先算库存/需求比、把"某语言见底"的风险前置**，否则跑到 90% 才发现只能改配比/补数据。出处：reports/2026-11-18-day2-tokenizer.md §3 · PLAN §5 风险表。
- **50M 的 tok/s 不是 140M 的 tok/s——决策门必须写清"在哪个模型上测"**（Day 2 校准，spec 写作教训）：吞吐 ∝ 1/(FLOPs/token)，140M 是 50M 的 2.74×。Day 1 实测有效算力 ~25 TFLOPS → 140M 理论仅 ~30k tok/s；若把 50M 的 35k 当门限放行，3B 实际要 ~64h。**门限要么直接在主模型上测（20~30 步探针仅 1~2 min），要么显式写折算系数**；指标不注明测量对象 = 没定义。出处：PLAN §4.1 · HANDOFF §4 门①口径行。

## 2026-11-19 · Day 7 · SFT 数据侧修正 / 评测 / GGUF

- **按"表面格式"降采样会误伤能力域——先保护能力域，再压风格**（Day 7 最重要教训）：SFT v2 为压"文化/艺术/交通"式罗列癖，把 assistant 任一段 ≥5 编号行的样本保留 1/5；结果 `math-add`/`math-mul` 从 v1 的 8/42 退化为 15/72——**长数学推理恰好都是编号列表**，被一起砍掉。修法 = v2b 增加"数学/推理样本"分类（用户句含数学关键词+数字，或答案含公式/等式），命中者**豁免列表降采样**，非数学列表仍保留 1/5；列表类占比 13.5% 仍 ≤15%。通用化：**采样规则要按"能力域"分类，而不是按"文本形状"一刀切**；先问"这条样本在教什么能力"，再决定降不降。出处：`reports/2026-11-19-day7-eval*.md` · `tools/build_sft_v2.py` `is_math()` · PROVENANCE v2b 段。
- **GGUF 导出必须按 llama.cpp 的 RoPE 布局重排 q/k 权重**（Day 7 部署坑）：直接写 GGUF（`gguf` Python writer）后模型能加载，但输出"前几个词正常、随后复读"（F16 与 Q4 同病）。根因 = llama.cpp 的 `LlamaModel.permute` 会把 q/k 权重按 head 重排 `[n_head,2,head_dim/2,in] → swapaxes(1,2)`（标准 Llama half-split RoPE ↔ llama.cpp 布局）；漏掉这一步，embedding/FFN 正常但注意力错位。补上 `permute_qk()` 后 F16/Q4 都恢复连贯。**"能加载/能跑"不等于"权重语义对"**；GGUF 导出要拿 PyTorch greedy 输出对拍。出处：`tools/export_gguf.py` `permute_qk` · llama.cpp `conversion/llama.py` L177-191 · `reports/2026-11-19-day7-deploy.md`。
- **评测 CSV 的表头必须与行字段数一致——否则下游 rubric 静默读错列**（Day 7 工具 bug）：`eval.py` 的 CSV 头是 5 列（model,test_id,tag,pass,answer），实际每行写了 8 列（多 decode/distinct2/rep4），rubric 脚本按 DictReader 读到 `test_id="greedy"`、`answer="1"`，整张表静默为空。**证据链工具的 schema 也要验收**：写完 CSV 后 `head -1` + 行字段数断言，比"看起来有文件"可靠。修法 = 头改成 8 列 + 答案截断从 200 提到 1000（列表 rubric 需要完整行）。出处：`tools/eval.py` CSV 段 · `reports/2026-11-19-day7-eval-rerun.csv`。
- **关键词判分同时有假阴性和假阳性——必须配语义 rubric + 编造检查**（Day 7 评测教训）：v2 的正确回答"2027 年没有世界杯。世界杯每四年举办一次，所以 2027 年没有冠军。"因 `expect_any` 缺"没有"被判 ❌；v1 的回答"没有官方的官方记录，但以下是 1958…"含"没有官方"却会命中，实际在编造。**只加关键词会把两者判反**。修法 = rubric 同时要求"承认不知道/纠正前提"**且**"无编造年份"；关键词分保留作覆盖指标，语义判定以 rubric 为准，报告并列两者。出处：`tools/eval_format.py` · `data/eval/tests.json` · `reports/2026-11-19-day7-eval-rubric-v2.md`。
- **单次 T0.7 采样不能用来做数据归因——身份/风格是随机变量**（Day 7 排查）：v2 step 1000/1500 采样说"通义千问"，一度怀疑数据漂移；查精确 prompt "你叫什么名字" 的 110 条对话，82.7% 是 MiniMind、Qwen 仅 0.9%；v1 step 3500 采样也说"通义千问"，最终 greedy 身份却是 jingyaogong。**看行为要用固定解码（greedy）或多次采样统计，不能用一条温度采样下结论**；训练早期身份未收敛，sample 只作现象观察。出处：`logs/sft-v2-run.log` · `logs/sft-v1-*.log` · 身份分布实测。

## 2026-11-20 · Day 8 · v2c 选择性保护与英文再平衡

- **组合记忆在容量边缘，微小分布扰动就翻转——单题修复的稳定性要用"多版小扰动"验证**（v2d 新发现）：`7×6=42` 在 v2b/v2c 两版稳定（输出"7 乘以 6 等于 42"），v2d 数学豁免量不变（6,264 vs v2c 6,243）、仅净增 ~2.3M token 杂样（translate/concise/format），就退回 v2 的同款错误值 **72**（= 6×12 的强先验干扰）。**140M 容量下"算术组合"记忆没有余量**：判定"数学修回"至少要两版同向，且报告里要写"该修复对数据分布扰动敏感"。出处：`reports/2026-11-20-v2d-eval.md`（math-mul 行）· `reports/2026-11-20-v2d.md` §4/§6。
- **"同方向样本上采样"教不会"指令行为"——行为修复要用目标行为的精确样本**（v2d 核心教训）：v2c 的 translate-en2zh 是"英答英"（方向丢了）；v2d 上采样英→中池 3×（702→2,106 条，全是"英问中答"杂样），结果输出变成"英文原句 + 中文字词解释"（"我的翻译是'我'在中文中是'我'的意思…"）——**方向修了、行为没学会**：池子里没有"把 X 翻译成中文 → 直接给译文"的指令样本，模型只能泛化出"英 prompt 要以中文回应"。通用化：**修"指令行为"要挖/造"指令 + 直接答案"的精确对**，泛化池只修方向先验。出处：`reports/2026-11-20-v2d-eval.md`（translate-en2zh 行）· `/tmp/v2d_recon2.py` 池形状。
- **长答案压制有效且可量化，但英文侧砍不到只能加正例**（v2d 方法学收获）：引导型长答案（prompt<120 字 ∧ 答案≥600 字）保留 1/2 → reason 复读 0.728→**0.088**、zh-fluency 0.516→0.303、decoder rep-4 0.135→0.084（砍 38%）；而英文长答案在前 810k 行写入 **0 条**（训练集里根本没有），en-fluency 的 0.708→0.371 完全靠 concise 英文正例对冲（20 条 ×3 的"2~3 句连贯答案"）。**"砍负例"与"加正例"是两种工具：负例在训练集里才砍得到，正例可以凭空造**。出处：`reports/2026-11-20-v2d.md` §1/§4 · `tools/gen_sft_v2_extra.py` `ZH_CONCISE_*`/`EN_CONCISE_FLU`。
- **预注册判据差 0.004 也按"未达"判——判据是闸门不是参考**（v2d 裁决）：rep-4 实测 **0.084** vs 判据 <0.08，同时 rubric 6/8 历史最高、语义题库 17/18——仍按预注册**不切换部署**。若因"接近"放行，判据就退化成事后解释工具（v2b 式复读回归的口子会重开）。**写判据时把"接近但不达"的情形也预先声明**（本判据天然含"差一点=没过"）。出处：`reports/2026-11-20-v2d.md` §5 · day8-review §7.1 预注册原文。

## 2026-11-20 · 机动窗口 · v2e 去污轮（评测污染发现 + 五项判据全过）

- **"按评测缺陷造数据"必须配评测集去重——否则指标退化为记忆测试**（v2e 开工发现，本项目最重要的方法学教训）：v2 起为修 v1 的缺陷造的 calibration/format extras 直接引用了评测原句——"请告诉我 2027 年世界杯的冠军。"（= refuse-unknown 原句）、ARITH 模板生成的"7 乘以 6 等于多少？只回答数字。"（= math-mul 原句）、"水的化学式是什么？"（= fact-water）、"列出三个学习编程的建议。"（= list-3）；v2d 的 concise 又加了 en-fluency/zh-fluency 原句。**后果：v2~v2d 的题库分含记忆成分，v1 的 16/18 反而是干净读数**。修法 = ①造数据按"能力/行为"写（同型变体：换知识点/换数字/换场景），不按"题目"写；②构建加硬断言（`assert_no_eval_leak`：extras 原句 norm 后不得与 tests.json prompt 互相包含，撞车即 AssertionError）；③报告里历史读数并列标注污染面。出处：`reports/2026-11-20-v2e.md` §1 · `tools/build_sft_v2.py` `assert_no_eval_leak`。
- **去污后五项判据全过——v2 时代的"能力不足"有一部分是假象**（v2e 结果）：同一底座、同一预算，v2e 在**无记忆样本**下拿到 rep-4 **0.055**（全系最低）/ 题库 **17/18** / translate "我热爱机器学习。" / math 8+42 / PPL +5.5%——math-mul 的 42 与 refuse 的"没有冠军"都是真泛化（ARITH 与 calibration 已排除对应组合）。**记忆样本能"修指标"但修不出能力；泛化机制（数学豁免 ×2 + 精确指令对 + 长答案压制）才修得出。** 出处：`reports/2026-11-20-v2e-eval.md` · `...-v2e-eval-rubric.md`。**（Day 11 修正：本条结论过度乐观——"去污"有 2 题残留 brevity 假阴性；math-add 8 是残留记忆、math-mul 42 是窄查表而非泛化；"真泛化"应只保留 calibration。见下方 Day 11 两条。）**
- **精确指令对 vs 方向池——v2d 的假设被 v2e 验证**（机制确认）：v2d 上采样 2,106 条"英问中答"杂样只修出"英文原句+中文字词解释"；v2e 加 180 条"指令+直接译文"精确对（30 unique ×6），translate-en2zh 一步到位输出"我热爱机器学习。"。**行为 = 指令-答案对的特异性信号，方向 = 语言配对的分布信号，两者不可互相替代。** 出处：`tools/gen_sft_v2_extra.py` `EN2ZH/ZH2EN` · `reports/2026-11-20-v2e.md` §4。

## 2026-11-20 · 最终阶段（spec 推进）· 部署 v2e-q8 + 量化保真度

- **量化会吃掉"弱记忆"——部署量化档要抽检"新学能力"，不能只看强先验**（本轮部署最重要的发现）：v2e GGUF 三档同 prompt 对拍（chat 模板 + greedy）——**F16 5/5 逐字一致**（导出/permute/tokenizer 链路忠实）；**Q8_0 保住全部新学能力**（math 42 / translate 中文）；**Q4_K_M 把 math 42 打回 72、translate 打回英文原句**。机理：v2e 的新能力（42、中文翻译）是与基座先验冲突的**弱记忆**，Q4 量化噪声足以让它退回强先验（72 = 6×12 的强模式）；Day 7 的"q4 与 PyTorch 一致"只因为 v2 的错误答案本身就是强先验。**验收协议升级：F16 逐字对拍（链路）+ 目标量化的"新学能力抽检"（本轮 = math/translate）；部署默认 Q8_0（173MB 多 70MB 换全部新能力）。** 出处：`reports/2026-11-20-deploy-v2e.md` §2/§3 · spec AC11。
- **对拍必须同模板同解码——裸 prompt 对拍会制造假不一致**（本轮方法坑）：第一轮用 `raw:true` + 裸 prompt 对拍，出现"你是谁？空输出 / 7×6 答成 5×6 / translate 复读环"的全量表观漂移，差点误判"导出链路坏了"；换回与 `eval.py` 完全一致的 chat 模板（`<|im_start|>user\n…<|im_end|>\n<|im_start|>assistant\n`）+ greedy 后，F16 立即 5/5 逐字一致。**对拍的三同原则 = 同 prompt 构造（含 chat 模板）× 同解码（greedy）× 同 tokenizer；任何一项不同，差异都归因不到导出/量化。** 出处：`reports/2026-11-20-deploy-v2e.md` §2 首段。
- **收尾阶段用 spec 固化"目标/非目标/可验证 AC/任务勾选"——交接成本降到最低**（本轮流程实践）：`specs/2026-11-20-final-phase.md` 把"部署切 v2e + 报告定稿"写成 AC1~AC11（每条带验证命令）+ T1~T4；执行时逐条勾选、AC 用命令验收（`ollama list`/`curl /health`/`grep`），新会话接卡即知"做到哪、怎么验、下一步是什么"。**spec 与 evidence 分离**：spec 是"要做什么+怎么验"（可随进度勾选），reports 是"做成了什么"（只增不改）；两者用 commit 串起来。出处：`specs/2026-11-20-final-phase.md` · commit `d0c973d`/`5fc4d2c`。

## 2026-11-20 · Day 10 · 终检（可复现性三连 / demo 温度 / LoRA 容量曲线）

- **"复现"要落到可对账的粒度，不是"跑通了"**（Day 10 终检方法）：终检把 §10 四段各做了一次对账——①数据构建 **bit-for-bit**（4/4 sha256 + meta 全字段相同，5.0 min）；②评测 **18/18 行逐字节相同**（含 answer 全文）；③部署 **F16 5/5 逐字一致**。**"跑通"只证明接口在，对账才证明"同输入→同输出"。** 注意边界：bit-for-bit 证明的是**流水线确定性**（固定 seed/遍历顺序/hash 函数），不证明**跨环境可移植**（换 tokenizer 文件、Python/依赖版本、机器仍可能变）；所以对账要连同"输入指纹"一起记（SHA256SUMS + ckpt sha + GGUF sha）。出处：`reports/2026-11-20-day10-repro-check.md`。
- **demo 的展示温度要按"行为漂移率"量化定档——展示质量也是终检对象**（Day 10 新发现）：demo 端 T0.7 下 translate 方向 11 次里 3 次输出英文（≈27%）；同 prompt 各 20 次对照 = **T0.7 16/20 中文方向 vs T0.3 20/20** → 默认温度下调 0.3。**"能对话"不等于"稳定给对方向"**：量化/部署验收用 greedy（三同对拍），但用户看到的 demo 是采样解码——展示参数必须单独做漂移率抽检，否则"模型会翻译"和"demo 常翻译错"可以同时为真。出处：`reports/2026-11-20-deploy-v2e-recheck.log` §3~§5 · `tools/app_stdlib.py`。
- **低秩容量是瓶颈之一，但不是 LoRA 1 epoch 欠拟合的主因**（Day 10 容量曲线）：r=8→r=12（+0.59% 可训练参数）只买到 val **−0.020**（1.8253→1.8054）、rubric 4→5、rep-4 0.260→0.249；距全参 1.6038 仍差 **0.20**，而同 step 1000 的差距（全参 1.7005 vs r8 1.8574 / r12 1.8422）在训练早期就已形成。**结论：1 epoch 内适配器学不会"模板+校准+格式"，加 rank 的边际收益递减；要补的是训练量（2 epochs）或把 LoRA 用在领域增量而非首次对齐。** 出处：`reports/2026-11-20-lora-r12-eval{,-rubric}.md` · REPORT §6。
- **dev 集修复 ≠ 能力——"去重"只证明不是记忆，"holdout"才能问是否泛化**（Day 10 最重要修正）：18 题 dev 集经八版迭代已接近开发集，所以新写 30 题未见题（三层双向去重 0 撞车：dev 集 / extras / SFT 源）重跑九版。结果：**v2e 与 v2 在 holdout 上同为 23/30（v2 修订版人工复核），dev 的 17 vs 15 优势不复现**；`13 乘以 5` 全错（56/40/35）、`17 加 6` 答 19、`100 减 37` 答 37——dev 的 math 42 不是 extras 记忆，但也不是算术，是窄查表；translate 只认精确指令句式（`Knowledge is power` 回英文）；**唯一稳定泛化的是 calibration（拒绝编造未来事实）**。通用化：**单题修复的验收要两级——①去重（不是记忆）②holdout（是否泛化）；dev 集只能证明"修了这个题"。** 出处：`reports/2026-11-20-holdout-audit.md` · REPORT §5.2。
- **关键词判分在未见题上假阳/假阴率很高——holdout 的分数必须配人工复核**（Day 10 评测方法）：30 题里 moon-count 有 7 个假阳（答案提到"月球"但数量答成 4/8/79 颗）、weather 有 2 个假阴（"今天阳光明媚"语义正确但词表缺该说法）、knowledge 有 2 个部分匹配（只译出"知识"漏"就是力量"）、reason 有 1 个偶然命中（废话里出现"备用"）。**关键词表是"提到检测器"，不是"正确检测器"；任何按单题下结论的地方，都要有 holdout + 人工语义复核兜底。** 出处：`reports/2026-11-20-holdout-audit.md` §3。

## 2026-11-20 · Day 11 · 收官后复核（去重假阴性 / 双向 / 分级）

- **"0 撞车"必须先证明检查器抓得到已知撞车——检查器本身会假阴性**（Day 11 最重要教训）：v2e 的 `assert_no_eval_leak` 有 `len(prompt)>=8` 守卫 + 只去空白的 norm，跳过了 6 字的「一年有几个月」和 7 字的「3 加 5 等于多少」，于是构建时断言通过、复扫报"0 撞车"，但这两题的 brevity 变体一直在 v2/v2b/v2c/v2d/v2e 训练集里。**任何"去重/校验通过"的结论，都要先喂一个已知违规样本做阳性对照**（本次修法：断言内置自测 + 新工具 `tools/check_eval_leak.py`）。出处：`reports/2026-11-20-eval-leak-recheck.md` §1。
- **去重必须双向，且要覆盖"前缀/少字"变体**：holdout 初版只查"评测 prompt 是否出现在训练内容里"，漏掉了 3 题"训练样本是评测题前缀"的近重复（calibration「请告诉我 2030 年世界杯的冠军。」vs 评测「……冠军是谁」；format「用一句话解释什么是光合作用。」vs 评测「请用一句话……」）和 1 条 concise（「介绍一下上海」）。**训练样本 ⊂ 评测题 与 评测题 ⊂ 训练样本 都是泄漏**；短句/礼貌前缀/数字嵌套要分别处理（数字嵌套如 3×3 ⊂ 13×3 是假阳，需人工排除）。出处：`reports/2026-11-20-eval-leak-recheck.md` §3。
- **"干净"要分级，不能二值化**（Day 11 报告修正）：完全干净（v1，无 extras）/ 部分干净（v2e，2 题残留）/ 含记忆（v2~v2d）。正确做法 = 标注每版的残留题 + 给"干净子集"读数（v2e 15/16 vs v1 14/16 vs v2 14/16），并相应降级判据解读（"五项全过"→"dev 字面全过、数学实质未过"）。**读数的诚实性不是"有没有记忆"，而是"记忆占多少、干净子集是多少"。** 出处：`reports/2026-11-20-eval-leak-recheck.md` §2 · REPORT §5.1。

## 2026-11-21 · Day 12 · 收官后深化（holdout 扩容 / LoRA 2ep / 分语言 val）

- **"无显著差异"可能是功效不足，不是真持平——先算 CI 再下持平结论**（Day 12 最重要的修正）：30 题 holdout 判"v2e 与 v2 同 23/30"（95% CI ≈ ±4 题 > 任何可能的差距）；扩到 90 题并人工校准后 **v2e 53 vs v2 47（+6 达预注册阈值 ≥5）**——dev 排名在未见题上部分复现。关键词原始分持平（59=59）是假象：v2 靠复读/回声碰词多拿 9 个假阳，v2e 复读最低所以假碰最少。**样本量要按"想检测的最小差值"倒推（p≈0.6 时检测 +6 需要 ≥70 题），30 题只能回答"有没有大差距"，不能回答"是否持平"。** 出处：`reports/2026-11-21-holdout-audit-v3.md` §3.4。
- **关键词假阳的大头 = 复读/回声碰词 + 数字嵌套；假阴的大头 = 数字写法收口缺失**（Day 12 扩容复核）：① Continent 题"70% 的陆地"骗过含"7"的 expect；② guitar 题全员答"inches 长度"（6.5 含 6）；③ mars 题 10/10 过——只因复读题干里的 "red"；④**光速题 9/10 版本答出 299,792（正确）而关键词全灭**（expect 只有 30万/300000/三十万/3×10，没有 299,792/299,792,458/每秒 30 万公里）——"知识掌握了、分数说没有"。规则：**expect_any 要收口"同一数值/概念的常见书写变体"（阿拉伯数字全半角、千分位、科学计数、口语单位）**；题干原词复读不等于作答。出处：audit-v3 §5。
- **预注册判据的基线要选"因果对照"，不是"最近的干净版本"**（Day 12 langval 判读修正）：预注册写的是"zh-PPL vs v1"——但 v1→v2（无英文上采样）本身就有 +5.7% sup 位移（列表降采样/校准注入的分布改变），按该口径会误报"英文上采样稀释中文"。正确基线 = **v2**（隔离上采样单变量）：zh sup ±0.15%，无稀释。**预注册时问一句"这个基线隔离了我想测的变量吗"**；若发现基线选错，两个口径都报告并声明修正，不静默换口径。出处：`reports/2026-11-21-langval.md` 判读节 · audit-v3 §6。
- **LoRA 欠拟合：rank 与 epochs 单独加码都不是主因——两条边际收益曲线都已枯竭**（Day 12 容量曲线）：r8→r12（+0.59% 参数）买 val −0.020；1ep→2ep（训练量 ×2）只买 **−0.013**；距全参仍差 0.19。但**能力维度 2 epochs 有实效**：holdout v3 人工 42→48（与 v2d 持平）、rep-4 0.249→0.176——**"LoRA 只适合领域增量"维持；若用 LoRA，2 epochs 是下限配置**。出处：`reports/2026-11-21-lora-r12-2ep.md` §3。
- **能力型 holdout 块要把"可用的探针"设计进题**（Day 12 出题经验）：①数学换序探针（3×13 vs dev 的 7×6）能区分"绑定字面"与"会乘法"——但两位数×个位数都会触发数字嵌套假阳（16×3 ⊃ 6×3），可用对极窄，设计前先过一遍检查器；②calibration 探针要避开 extras 的年份覆盖（2027~2042 全占）→ 用 2044+；③`今天非常冷`→全员 hot 的"先验反扑"探针（与 Q4 量化 42→72 同型）值得保留——**弱记忆 vs 强先验的冲突题是测"真学没学"的最锐利探针**。出处：spec `specs/2026-11-21-post-final-deepening.md` §7 · audit-v3 §3.2。
